# Reincarnation 开发与实现说明

Minecraft **26.1.2** / NeoForge **26.1.2.99** / Java **25**。

需要安装 **Jupiter 2.4+** 和 **Saturn 1.2.5+**，客户端与服务端均需要；客户端额外需要 **ApricityUI 1.2.9+**。开发依赖使用 CurseMaven 文件：Jupiter `8569832`（2.4.2）、Saturn `9449659`（1.2.5），AUI 使用 `com.sighs:ApricityUI-neoforge-26.1:1.2.9`。

稳定账号 UUID，以世代区分每一世。已实现通用 `EntityReference` 世代持久化、玩家转生与进度重置、旧世归档、事务恢复、文字查询，以及基于 AUI 和 Saturn 信息文档的世代查看界面。原版 UUID 字段形状与引用网络协议保持不变；引用持久化无需逐实体或逐字段适配。

引用元数据使用 `ReferenceMetadata.CODEC` 和 `ReferenceStamp.MAP_CODEC` 定义结构，通过 `Codec.encode(..., prefix)` 先合并扩展区、再合并完整载荷。已删除手写 NBT 读写的 `ReferenceNbt`，由不依赖 NBT 类型的 `ReferencePersistence` 使用 DynamicOps 收集路径、检查对应目标并返回结果；原版 UUID 仍为四整数数组。第三方完整对象可使用 `ReferencePersistence.wrap(codec)` 联合编解码，标准实体和 SavedData 路径自动接入。

`ReincarnationService` 使用当前服务端生命周期内的单例：`ServerAboutToStartEvent` 调用 `start(server)` 创建并恢复事务，业务代码通过无参 `get()` 取得实例，`ServerStoppedEvent` 调用 `stop()` 释放。移除了按服务器保存服务的 Map；重新进入存档时创建新实例，不沿用之前的运行状态。`ReincarnationApi.view(account, generation)` 也不再需要传入服务器。

## 指令

| 指令 | 用途 |
|---|---|
| `/reincarnation` 或 `/reincarnation status` | 查询自己的当前世 |
| `/reincarnation status <玩家名或UUID>` | 查询指定玩家当前世及待恢复状态 |
| `/reincarnation history [玩家名或UUID] [页码]` | 默认每页 8 条世代摘要，可配置；省略玩家时查询自己 |
| `/reincarnation info <玩家名或UUID> <世代编号>` | 查询某一世详情 |
| `/reincarnation view [玩家名或UUID] [世代编号] [列表页码]` | 打开世代档案界面；省略玩家时查看自己，省略世代时查看当前世，省略页码时定位所选世代 |
| `/reincarnation rebirth [在线玩家] [原因]` | 转生到世界出生点，省略目标时转生自己 |

初始为 **第 1 世**，首次转生后为第 2 世；`info` 的世代编号也从 1 开始，例如 `/reincarnation info <玩家名或UUID> 1` 查询第一世。存档内部世代 ID 仍从 0 开始，兼容已有存档与引用，无需迁移。普通玩家可查询自己；查他人和执行转生需要游戏管理员权限（原版等级 2）。控制台需指定玩家。离线查询使用已有记录，支持名字补全和 UUID，不请求远程账号服务。

详情显示开始记录/结束时间、原因、维度与位置、游戏模式、经验、背包物品数、完成进度数、死亡次数和游戏时间。安装前的历史无法追溯；离线摘要来自最近一次登录、退出、自动保存或查询。

`view` 需要由游戏内玩家执行，世代同样从 1 开始，例如 `/reincarnation view <玩家名或UUID> 1` 查看第一世。新归档保存不可变的 Saturn 快照；旧归档直接解析已有 NBT、统计和进度，不创建历史 Player，也不借用今世实体。仅有摘要或当前玩家离线时明确标为“仅摘要”，未记录的健康、背包明细等保持缺失。展示扩展统一使用 Saturn 注册的行与 `InformationGroup`，因此其他模组接入后可直接出现在此界面。

界面使用 AUI 内置 Ore 主题，并适配 Minecraft GUI 字号与按钮尺寸。左侧按从新到旧排列世代，包含当前世；每页最多 32 条摘要，点击切换详情，并显示状态与结束原因。右侧按照信息文档的 Group 顺序分组，点击标题展开或折叠，也可以全部展开/折叠；默认展开世代记录与基本信息。两侧独立平滑滚动，分组展开/折叠时播放高度与箭头旋转动画，切换世代保留分组展开状态。相同信息行属于多个 Group 时，在各组分别显示。页面保留文本颜色与格式，长标签和值直接换行，不显示重复的 Tooltip；列表、物品槽位和表格使用 Saturn 的文字投影展示，不包含人物三维预览。

页面采用紧凑排版：正文和按钮文字为 8px，主标题为 10px；详情行高 15、分组标题高 20、左侧世代项高 30。顶部按钮、栏目标题和两栏间距同步收紧。换行、省略号与按钮宽度按实际字号换算，滚动范围、点击区域和折叠动画使用同一组行高。

查看在线玩家的当前世时，每 **20 个客户端 tick** 请求一次最新信息，通常约每秒更新。后台响应只更新所选世代摘要与 Saturn 信息文档，不重新打开界面、不显示加载提示，保留列表页码、两侧滚动位置、分组展开状态与动画。是否为当前世由服务端明确标记，不依赖当前列表页是否包含所选世代；查看历史世代不轮询。当前世结束后接收最后一次归档信息并停止刷新，目标离线或权限失效时也停止，重新打开界面可重新查询。

信息页由服务端鉴权、校验归档并收集展示行后，通过 Saturn 的开屏消息发送所选世代的信息文档和当前页摘要，不发送原始归档或整份附件。翻页和切换世代再次走服务端指令检查；单次展示内容编码后超过 1,000,000 字节时明确拒绝，避免静默截断。

自动刷新使用本模组的 `life_view_refresh_request` / `life_view_refresh_update` 消息，每次重新检查本人/管理员权限，服务端主线程从当前实体重新收集信息；正常刷新不读历史列表、不写当前世摘要。请求携带唯一 ID，同一界面最多一个刷新请求在途，100 tick 超时后允许重试；关闭界面、切换世代或翻页后丢弃旧响应。刷新响应同样限制在 1,000,000 字节内，失败时停止后台刷新，保留已有展示。

提供简体中文与英文翻译，命令、错误和恢复断线提示使用翻译键，由客户端按语言设置显示；游戏模式复用原版翻译。转生原因统一使用 `Component`，通过 `ComponentSerialization.CODEC` 保存完整的翻译参数、回退文字和样式；默认原因使用可翻译组件，玩家手填原因使用原文组件。旧版原文可直接读取，摘要仍兼容独立的 `reason_key`；请求不再处理旧 `reason_translation_key`，该字段按未知键忽略。新数据只写一个 `reason` 字段。

## 默认行为与扩展

先归档当前内存中的玩家 NBT、统计、进度和处理器数据，再推进世代，使用原版 `respawn` 创建新玩家并更新连接。转生专用钩子跳过 `ServerPlayer.restoreFrom` 的整批继承，以构造器默认值为起点，仅补回策略允许的数据；背包、末影箱、经验、配方、成长属性和旧世状态从未复制进新对象，`keepInventory` 也不触发继承。统计和进度按账号缓存，创建新玩家前仍需驱逐旧缓存并初始化对应文件。

`PlayerInheritance` 代替原来的 `PlayerReset`：仅交接聊天会话、区块跟踪、调试订阅和 Tab 页眉页脚等连接运行状态，按策略恢复游戏模式、未知 NeoForgeData 和符合标签规则的附件。玩家账号、客户端设置和实体 ID 继续由原版重生流程交接；不加载旧玩家完整 NBT，也不逐项清空新玩家字段。开启清未知数据时只是不导入旧数据，构造和事件监听器生成的新数据继续保留。

默认清个人分数，保留队伍、游戏模式、权限和账号事实。未知模组持久化 NBT 默认保留，**Attachment 默认全部清除**；仅 `reincarnation:keep_on_rebirth` 标签内、类型声明 `copyOnDeath()` 且复制处理器允许复制的附件自动保留。模组玩法规则通过版本化 `ReincarnationHandler` 注册。裸 UUID、外部数据库、修仙模组和 Curios 的具体语义需由对应处理器实现。

标签文件为 `data/reincarnation/tags/neoforge/attachment_types/keep_on_rebirth.json`，默认是空集合。其他模组或数据包可用同一路径扩展：

```json
{
  "replace": false,
  "values": [{ "id": "othermod:player_data", "required": false }]
}
```

标签可通过 `/reload` 重载，新事务将保留名单随归档保存，恢复时不受后续标签变化影响。开启 `reset.unknown_mod_data` 会同时禁止标签自动保留；处理器仍可显式恢复数据。正常转生在 Clone 前从归档恢复白名单附件，并跳过 NeoForge 默认 Clone 监听器的自动附件复制，每个保留项的复制处理器只执行一次；不再移除新玩家已有附件。其他模组显式编写的 Clone/Respawn 初始化继续执行并保留，普通死亡重生仍遵循 NeoForge 自身的附件复制规则。

重生位置、登录恢复和退出记录监听使用 `EventPriority.LOWEST`。正常转生的策略数据在 Clone 前补入，原版 `respawn` 返回后才执行处理器、Reset 事件并保存新世，此时 Clone 与 Respawn 事件的所有同步监听器已结束，不再清理它们为新玩家初始化的数据。故障恢复在首次登录式的新对象上补回归档中的允许项，同样保留新登录初始化的数据。

旧世引用统一失效。已加载宠物、马和持久愤怒状态会清理；之后加载的实体在服务端 tick 清理。新世可建立新关系，不清空 Vault 等账号领奖集合。

事务失败后阻止半成品保存并断开连接，重新登录或重启继续同一事务。新世已保存时只补齐记录，不再次清空。损坏索引/归档或缺失必要处理器会阻止恢复。

```java
// 服务端主线程调用，之后使用返回的新玩家对象。
ServerPlayer fresh = ReincarnationApi.reincarnate(player,
        ReincarnationRequest.atSpawn(player, Component.literal("寿元耗尽")));
```

`ReincarnationRequest` 和 `SoulRecord` 均只保留 `Component reason`，已删除 `reasonTranslationKey` 与 String 原因的旧重载。可翻译原因直接传 `Component.translatable("yourmod:reason")`；需要回退文字时使用 `Component.translatableWithFallback(...)`，查询和界面直接展示归档中的组件。

请求可指定维度、位置和 `ResetPolicy`。通过模组事件总线的 `RegisterReincarnationHandlersEvent` 登记处理器；`Pre` 可取消、`Reset` 必须幂等、`Post` 只作通知。不要单独用 `Generations.commit` 代替转生。完整契约见 [实现报告](转生系统调研/07-转生流程与历史查询实现.md)。

## 寿元系统

寿元展示统一为「当前年龄 / 总寿元」：初始显示 0 / 60 岁，随着老化正向增加年龄；增寿只提高总寿元，新世年龄归零。年龄由总额减剩余计算，信息行、前世档案、查询与提醒使用同一显示出口。

寿元核心由本模组提供，活体账本、自然老化、提醒、耗尽后果、数据表行为/条件和 PlayerView 展示均可独立使用。`LifespanApi` 提供只读 get、set/add/unlimited、立即 rebirth 与排队 requestRebirth；完整换世会返回新玩家，实体 tick、行为链和脚本应使用排队入口。

默认禁用自然老化。启用后初始寿元 1440000 刻，按 24000 刻/岁显示为 60 岁；每 20 刻扣 20 刻，离线不补扣。可配置玩家寿尽正常死亡或旁观、完整换世或原地重置、创造和旁观是否老化。`/lifespan` 全部节点需要管理员权限，支持 get/set/add/unlimited/reincarnate；reincarnate 反馈表示接受请求。

`warning_fraction=0.1` 表示剩余寿元不高于总额的 10% 时，在聊天栏提醒一次。已处于低寿元的登录或配置变更也会补发；同一段低寿元状态不反复刷屏，增寿恢复到阈值以上后重新允许提醒。0 关闭提醒，1 在有限账本开启时即可提醒；无限寿元和总额为 0 时不提醒。提醒状态仅在当前附件对象中保存，不写入存档，不改变账本的两个 long 字段。

寿尽直接转世与寿尽死亡后的自动转生均记录 `reason.reincarnation.lifespan`（“寿元耗尽”）。死亡事件在最低优先级识别 `reincarnation:lifespan` 伤害，将原因组件存入可持久化、不会随重生复制的 `reincarnation:death_reason` 附件；协调器使用该组件创建转生请求。这样死亡界面停留超过原版最近伤害来源的 40 tick 有效期，仍能保留准确原因；普通死亡继续记录“死亡转生”，新玩家不继承上次的死亡原因。

新增 4 个 action：`reincarnation:add_lifespan`、`reincarnation:remove_lifespan`、`reincarnation:reincarnate`、`reincarnation:unlimited_lifespan`；3 个 condition：`reincarnation:lifespan`、`reincarnation:lifespan_state`、`reincarnation:generation`。寿尽击杀使用独立 `reincarnation:lifespan` 伤害类型。普通死亡保留账本，完整换世重开并将旧账本保存在前世归档中。

MiXianTu 改为调用共享寿元 API，并用 handler 保存修炼数据保留策略；旧 `mxt:lifespan` 附件可迁移。灵草补算上限独立归 MiXianTu 炼丹配置。完整 API、JSON 和事件契约见 [寿元实现说明](转生系统调研/15-寿元系统迁移与数据驱动联动.md)。

## 配置

Jupiter 自动生成 `config/reincarnation/reincarnation-server.json`：

```json
{
  "lifespan": {
    "enabled": false,
    "base_lifespan": 1440000,
    "settle_interval": 20,
    "age_per_settle": 20,
    "on_expire": "DEATH",
    "player_death_mode": "KILL",
    "player_rebirth_mode": "NEW_LIFE",
    "warning_fraction": 0.1,
    "ticks_per_year": 24000,
    "age_creative": false,
    "age_spectator": false
  },
  "lifecycle": {
    "auto_reincarnate_on_death": false,
    "filter_death_damage_types": false
  },
  "reset": {
    "scores": true,
    "team": false,
    "unknown_mod_data": false,
    "keep_game_mode": true,
    "clear_resources": true
  },
  "query": {
    "history_page_size": 8
  }
}
```

`reset` 控制清个人分数、移出队伍、清未知模组数据、保留游戏模式和清资源。`clear_resources` 默认 true，关闭时按统一附件机制保留 Saturn 资源；标签仍可单独指定资源保留，未知模组数据重置优先。原地重置也清理未保留附件并重建 Saturn 技能和被动；`lifespan.kill_on_reset` 默认 false，开启后在原地重置完成时以寿元伤害击杀，完整换世不额外击杀。分页大小范围为 1–50。默认值延续原有行为。

`lifecycle.auto_reincarnate_on_death` 默认关闭。开启后，符合条件的死亡重生会自动执行完整转生、推进一世并归档，普通原因显示为“死亡转生”，寿尽显示为“寿元耗尽”；保留原版死亡界面，末地返回不触发。即使 `keepInventory` 开启，转生仍会清空新世背包等进度。自动转生遵守 `Pre` 取消和事务恢复规则；极限模式保留原版观战处理。旧配置在启动时保留已有值并补齐新增字段。

`lifecycle.filter_death_damage_types` 默认关闭；与自动死亡转生同时开启时，只允许最终致死伤害类型属于 `reincarnation:reincarnate_on_death` 的死亡进入转生。未命中、tag 为空或旧死亡记录没有类型时走原版普通重生，不推进世代、不生成归档。手动指令/API 和寿元 `on_expire=REINCARNATE` 的直接转世不受此筛选影响，已提交事务也继续恢复。

数据包路径为 `data/reincarnation/tags/damage_type/reincarnate_on_death.json`，默认内容如下；可追加原版或其他模组的 damage type ID，`replace: true` 可覆盖整份名单，`/reload` 后生效：

```json
{
  "replace": false,
  "values": ["reincarnation:lifespan"]
}
```

最低优先级死亡事件将最终伤害的注册表键写入 `reincarnation:death_damage_type` 附件，使用 `ResourceKey.codec(Registries.DAMAGE_TYPE)` 持久化，不复制到重生玩家。之前的非致死攻击不记录；等待死亡界面超过 40 tick 或保存后重载仍可判定。重生入口使用当前注册表重新解析该键并查询 tag，因此死亡后修改名单也按重生时的名单生效。

可从模组列表的配置按钮进入 Jupiter 配置界面；远程配置按 Jupiter 的管理员权限检查开放。手动修改服务端文件后执行 `/reload`。重置策略由 `ReincarnationRequest.atSpawn` 在请求创建时读取并随事务持久化，后续配置修改只影响新请求；显式传入 `ResetPolicy` 的 API 调用使用调用者指定的策略。
