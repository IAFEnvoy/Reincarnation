# 通用 EntityReference 持久化桥接

> 2026-11-01；Minecraft 26.1.2、NeoForge 26.1.2.99、Java 25。
> 本报告承接“不改变原版字段结构”和“不逐个实体/关系兼容”的要求。取代 04 报告中将槽位适配器作为主线的建议；其中关于原版 UUID、保存顺序和复制行为的源码证据仍有效。
> 2026-11-02：已开始实际实现，9 个集中 Mixin 与独立世代索引已接入，首轮 7 项专服 GameTest 通过。下文的 21 项是研究原型，最新实现状态和覆盖范围见 [06-通用引用桥接实现与验证](06-通用引用桥接实现与验证.md)。

## 1. 结论与通用范围

**建议采用“EntityReference 编解码桥接 + NBT 节点临时标记 + 完整载荷元数据表”的通用方案。** 原版 UUID 字段、列表、Map 和网络引用格式保持原样；世代仍在引用的运行时扩展字段中，并在完整对象的扩展数据区集中持久化。

对通过 `EntityReference.codec()` 及原版 `store/read` 路径保存的 NBT 引用，持久化层无需知道这是狼的主人、狐狸信任列表、投射物来源，还是第三方新增字段。字段和列表索引由实际 NBT 树自动生成，不逐类登记关系槽位。

这不是“保留叶子 UUID 值就能凭空保存额外信息”。完整载荷仍需要一个扩展元数据区；这里采用已有 `NeoForgeData` 内的 `reincarnation:reference_metadata`。如果连扩展区都不允许出现额外数据，只能使用外部旁库，并接受 04 报告的身份边界。

## 2. 统一流程

```text
保存：
EntityReference(UUID, generation)
  → 桥接 Codec 委托原版 UUID 编码
  → 输出仍为四整数 UUID，只在内存 NBT 节点上附加临时标记
  → 完整对象组装完成后统一扫描树
  → 自动生成“路径 + 目标 UUID + generation”元数据表
  → 在对象扩展区写入这张表，正常保存 NBT

读取：
取得完整 NBT
  → 在任何引用解码前统一读取元数据表
  → 按路径与目标 UUID 校验，恢复 NBT 节点的临时标记
  → 原版对象/列表/Map Codec 正常解码
  → 桥接 Codec 将节点标记恢复到 EntityReference 扩展字段
  → getEntity / matches 集中校验玩家当前世代
```

元数据不是通过全局玩家 UUID 映射回填，也不是在读档时补当前世代；它记录每个具体引用值原本携带的绑定世代。

## 3. 保存布局

```snbt
{
    Owner: [I; 123, 456, 789, 1011],
    Trusted: [[I; 123, 456, 789, 1011]],
    NeoForgeData: {
        "reincarnation:reference_metadata": {
            version: 1,
            entries: [
                {
                    path: [{key: "Owner"}],
                    target: [I; 123, 456, 789, 1011],
                    generation: 2L
                },
                {
                    path: [{key: "Trusted"}, {index: 0}],
                    target: [I; 123, 456, 789, 1011],
                    generation: 3L
                }
            ]
        }
    }
}
```

同一个 UUID 在不同位置出现，可以携带不同世代。路径按有类型的分段保存，明确区分字符串键和列表下标，不能简单用 `/` 拼字符串，也不能按 UUID 合并记录。

这里只示范结构，不要求同一个实体原本同时拥有 Owner/Trusted。真实字段、嵌套 Map 和列表均由通用遍历发现。新增元数据只占本模组命名空间，不覆盖其他 NeoForgeData 内容；原版字段删除本模组元数据后应与原始树相等。

## 4. 集中接入点

| 基础入口 | 工作 | 为什么可以通用 |
|---|---|---|
| `EntityReference.of(T)` | 新引用指向 ServerPlayer 时捕获权威当前世代 | 原版主人、投射物、信任、伤害归属等都以实际实体建立引用，无需判断关系种类 |
| `EntityReference.codec()` | 包装原版 UUID 编解码，向输出节点标记/从输入节点还原世代 | `listOf`、Map、RecordCodecBuilder 组合会自动继续调用同一叶子 Codec |
| `EntityReference.store` | 将原本绕过引用 Codec 的 UUID 写入改为调用桥接 Codec，保持编码形状 | 一处处理所有通过此方法保存的引用 |
| `readWithOldOwnerConversion` | 首先通过桥接 Codec 读取 UUID，再保留旧玩家名转换 | 一处覆盖原版旧主人转换，不逐个修改宠物 |
| `IntArrayTag.copy()` | 将内存临时标记传给复制结果，不改 write/equals/hashCode | CompoundTag 深拷贝及 merge 会调用底层 copy |
| `NbtOps.convertTo` 等 NBT→NBT 转换 | 在输出仍为同一 UUID 时传递临时标记 | 防止重建 int 数组节点时丢失世代 |
| 完整对象输出/输入边界 | 扫描打包元数据；解码前恢复节点标记 | 不依赖字段名、实体种类、模组命名空间或关系槽位 |
| `getEntity` 两个重载、`matches` | 缓存命中和普通解析都执行世代检查 | 统一执行关系失效规则 |

原版 `codec()` 的缓存初始化仍需提前完成 Mixin；不要服务器启动后才替换。包装器应直接委托原始 UUID 编解码实现，避免递归调用自己。

### 临时标记如何存

正式实现可用 Mixin 给 `IntArrayTag` 增加一个 `@Unique` 可空字段，保存目标 UUID 和 generation；只给引用 Codec 产生的 UUID 节点赋值。该字段不参与 NBT 二进制 write、equals、hashCode 或 size，因此不会把 UUID 数组变长或改成对象。

不能用按 Tag.equals 比较的普通 Map 存标记：值相同的两个 UUID Tag 可能分别属于不同世代。原型使用 IdentityHashMap 模拟 Mixin 字段；正式实现不应照搬长期强引用的全局 Map，否则会持有旧节点和引用对象。

数组原始内容可以被修改，所以复制、收集和解码时都应检查标记内目标 UUID 与当前四整数值一致。不一致则进入损坏/无效分支，不能给新值套上旧戳。

## 5. 根边界与复制问题必须解决

### 为什么不能只改 codec 返回值

`.99 IntArrayTag.java:87-90` 的 `copy()` 创建全新的对象；`CompoundTag.java:418-421,459-465` 的 copy/merge 会递归复制。原型确认，只有临时身份表而没有复制桥接时，所有标记都会丢失。因此底层复制传播属于方案必要部分，不能只在某个宠物处补代码。

`NbtOps.java:123-124` 的转换还会重建 UUID 数组，应覆盖 NBT→NBT 的这条基础路径。任意第三方将 UUID 拆成 int 再自行重组，已经绕过了受支持的复制/引用序列化契约，不能凭相同整数自动判断它是否是同一条历史引用。

### 完整载荷何时打包

`TagValueOutput.buildResult()`（`:159`）和 `TagValueInput.create()` 两个入口（`:40-45`）是优先研究的通用边界。打包在关系字段全部编码以后完成；读取在关系第一次解码以前完成，因此不会遇到 04 报告中“附件早于 addAdditionalSaveData 保存”或“TAIL 恢复晚于愤怒首次解析”的问题。

需要覆盖不经过这套 ValueInput/Output 的基础持久化入口。例如 `SavedDataStorage.encodeUnchecked` 在 `.99 :220-225` 直接用 Codec 写 `data` 字段，应在这类完整存档封装层使用同一打包函数；读取端 `readSavedData` 在 `:95-105` 将完整封装中的 `data` 交给 Codec 前，先运行对应恢复函数。路径相对完整封装，不能只把 `data` 子树交给恢复函数。通过少数持久化基础设施接入，而不是逐个 SavedData 类型或每个引用字段接入。

`TagValueOutput.buildResult()` 不是“今后不会再修改”的绝对边界。对象打包后又被复制、裁剪、嵌套或改列表时，需要在最终受支持的完整载荷边界再次按节点标记重建路径；读取边界递归识别已嵌套载荷的元数据。元数据中目标不符或路径失效时拒绝应用，不能猜测配对。

不能给任意中间 Map 直接增加元数据键：`Codec.unboundedMap` 可能把它当成业务条目解码。元数据只放在已知允许扩展的完整对象区；世界 SavedData 的外层封装、实体/方块实体的 NeoForgeData 都由基础持久化边界选择，内部 Map 的结构保持原样。

保存在线程切换前形成不可变快照或私有副本；元数据扫描不能一边在后台修改，一边由主线程重排同一载荷。重复打包应幂等，并跳过元数据表自身，避免嵌套增长。

### 防止旧路径覆盖新引用

恢复和打包必须区分输入阶段与运行中阶段。原始载荷先恢复自身及全部嵌套元数据，完成后才能复制、重排列表或替换引用；后续内存节点戳才是重建路径的来源，不能把旧表再次套到已经修改的树上。同 UUID 的引用换了世代，单靠目标 UUID 校验也发现不了这种错误。

正式实现需在工作副本中消费/移除已恢复的本模组元数据，或用能随受支持复制传播的恢复状态保证不重复应用旧表。重新打包清理旧表，仅从当前节点戳生成新表，无引用时删除空表；未恢复的外来载荷必须先进入完整输入流程。嵌套内外表对同一节点记录同一世代可去重，记录不同世代则报告冲突并隔离，不能靠遍历顺序决定覆盖结果。表格式、路径类型、重复记录和未知版本也要验证。

解码失败有时会被 `ValueInput` 记录后按缺字段继续加载，因此“桥接 Codec 返回错误”本身不等于完成隔离。无效节点状态需随复制传播；若不能确定损坏记录影响的具体叶子，应隔离该完整载荷或进入显式恢复流程。不能丢弃错误后将它重新编码为无戳旧档。这些属于正式实现的验收约束，当前 21 项原型未完整实现上述状态与损坏传播机制。

## 6. 为什么新增模组字段不需要专门适配

第三方增加 `Codec.unboundedMap(Codec.STRING, EntityReference.codec().listOf())` 时，保存过程中相同的引用叶子自动被标记，树扫描会得到它真正的位置。字段改名、列表顺序变化和嵌套结构变化，都会在新的保存结果中重新生成路径；不维护硬编码字段清单。

对已经携带嵌套元数据的载荷，完整读取入口先恢复所有节点标记；随后引用 Codec 还原世代。只要搬运走标准的 NBT 复制和完整载荷边界，标记可跟随子树移动，并在下一次保存时获得新路径。

蜂巢的 UUID 剥离不再要求靠原蜜蜂 UUID 查询外部旁库：戳记录在载荷内部。按源码，NeoForgeData 不在蜂巢剥离名单中（`BeehiveBlockEntity.java:55-82,394-416`）；是否覆盖整条蜂巢→物品→跨维度→释放链路，仍需游戏验证。

## 7. 通用性边界

- **输入必须仍是 EntityReference**。裸 UUID 的流言、领奖集合和 Brain 记忆不自动获得关系世代；不能把全部 UUID 都加上玩家世代，否则会误改账号级事实。
- `of(UUID)` 没有服务器上下文，不能普遍推导创建时的世代。解码从元数据恢复；确实新建的 UUID 关系需要有上下文的通用绑定 API。原版本次检索的关系绑定通过 `of(实体)`，不需要逐类提供绑定代码。
- **NBT 和 JSON 是不同的承载后端**。本轮通用原型验证 NBT；只有 UUID 数组的 JSON 叶子同样没有额外位置，若要支持完整 JSON 持久化，需增加对应的统一对象封装/节点上下文后端，不能直接承诺 NBT 标记会跨格式保留。
- 不修改原版引用 StreamCodec；服务端磁盘戳和客户端显示可分开。网络交互仍遵循服务端权威，不依赖客户端回传 generation。
- 保留 UUID equals/hashCode 时，同 UUID 新世代引用的 `SynchedEntityData.set` 可能被当成相等。应在该基础数据更新入口集中识别引用/Optional 引用的世代变化，不能又退回每个宠物 setter 补发包。第三方自定义数据包装类型需要遵守明确的元数据变化通知契约。
- 统一引用失效不能代替玩法附属状态清理，例如宠物驯服标志、AI 当前目标和末影珍珠票据。持久化兼容层无需逐关系适配；清理某项具体玩法副作用则仍由该系统负责。

DataFixer、第三方 NBT 过滤器或跨格式重编码若移走/丢弃元数据，无法靠 UUID 值自动重建原世代。需要保留格式版本、目标校验和迁移门槛；不能在读取时把缺失信息补成当前世代。

## 8. 本轮验证

独立算法原型：`.gradle/generic-ref-nbt-probe/probe/GenericReferenceNbtProbe.java`。

```powershell
.\gradlew.bat --offline --no-configuration-cache -I .gradle/generic-ref-nbt-probe/generic-probe.init.gradle verifyGenericReferenceNbtProbe
```

当前工程真实依赖与 Java 25 下编译运行成功，**21 项检查通过**，覆盖：

- 使用原版 EntityReference Codec 委托编码，完整原有 NBT 树保持相等。
- 无字段/槽位专用代码，发现标量、列表与任意嵌套 Map 中的六条引用。
- 相同 UUID 的不同世代引用分别还原；世代 0、包含 `/` 的字符串键和列表下标正确区分。
- 压缩 NBT 真实二进制写出、清空内存身份表、读回和还原后，世代仍存在。
- 复制传播的必要性、通用复制桥接、子树移动后自动生成新路径、重复打包幂等。
- 保留其他 NeoForgeData 与任意未知业务键；仅删除本模组元数据即可恢复原树。
- 目标 UUID 不符、负世代拒绝应用；旧 UUID 格式可读取；六整数 UUID 数组被原版拒绝。

**验证限度**：原型以身份表模拟 `EntityReference`/NBT 节点的 Mixin 字段，以通用复制函数模拟 copy 钩子；没有应用实际 Mixin，也没有启动专服/客户端。原型证明算法与原版数据布局可共存，不代表所有存档边界、NbtOps 转换和玩法副作用已完成接线。下一步应优先验证这些集中钩子，而不是新增逐实体持久化适配器。
