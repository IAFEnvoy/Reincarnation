# Identity & persistence trace

Scope: Minecraft 26.1.2 decompiled sources with NeoForge patches (`E:\Java\_mcsrc_26.1.2\net\minecraft\...`),
NeoForge 26.1.2.114 API sources (`E:\Java\_nfsrc_26.1.2\net\neoforged\...`), and (for one narrow external
fact) authlib 7.0.63 from the local Gradle cache. All paths below are relative to those two roots.

**Headline answer**

* The player's UUID is fixed twice, both from the `GameProfile`: once in the `Player` constructor
  (`Player.java:182`) and once again, unconditionally, when playerdata NBT is loaded
  (`Player.java:649`). Everything persistent on the server is keyed off the `Entity#uuid` field, which
  normally equals the Mojang (session-service) profile UUID, or `UUID.nameUUIDFromBytes("OfflinePlayer:" + name)`
  in offline mode.
* `getPlayerForLogin` **no longer exists** in 26.1.2. The `ServerPlayer` is constructed in
  `PrepareSpawnTask.Ready#spawn` from `cookie.gameProfile()`, and player data is loaded there and in
  `PlayerList.loadPlayerData`.
* A mod can change the *entity* UUID at runtime via `Entity#setUUID` (public), but not the profile UUID
  (authlib 7.x `GameProfile` is a `final` record — no setters), and the change is reverted on the next
  save/load round trip because `Player#readAdditionalSaveData` re-derives it from the profile.

### 1.2 Offline mode — deterministic UUID v3 derived from the name

Three fallback sites all call `UUIDUtil.createOfflineProfile(name)`:
`ServerLoginPacketListenerImpl.java:130` (server does not use authentication, or memory connection),
`:210` (session verification failed but singleplayer), and `:218` (auth servers unavailable but singleplayer).

```java
// UUIDUtil.java:86-93
public static UUID createOfflinePlayerUUID(String playerName) {
    return UUID.nameUUIDFromBytes(("OfflinePlayer:" + playerName).getBytes(StandardCharsets.UTF_8));
}

public static GameProfile createOfflineProfile(String playerName) {
    UUID id = createOfflinePlayerUUID(playerName);
    return new GameProfile(id, playerName);
}
```

The prefix constant is at `UUIDUtil.java:52`: `private static final String UUID_PREFIX_OFFLINE_PLAYER = "OfflinePlayer:";`
(note the literal is inlined in `createOfflinePlayerUUID`, the constant is only used elsewhere).
So in offline mode the UUID is a pure function of the exact username string — case sensitive, and
`NameAndId.createOffline` (`NameAndId.java:47-50`) uses the identical derivation, which is what keeps the
usercache consistent with the login UUID offline.

Singleplayer also short-circuits: if the requested name equals `getSingleplayerProfile().name()`, the
world's stored profile is used verbatim (`ServerLoginPacketListenerImpl.java:122-124`; the profile is set
via `MinecraftServer#setSingleplayerProfile`, `MinecraftServer.java:1316-1318`).

## 2. Can a mod replace the `GameProfile`/UUID before playerdata load / `ServerPlayer` creation?

**Short answer: NeoForge 26.1.2.114 provides no event in the login path for this.** There is no
"login event" that hands a mod a mutable profile before the spawn task runs.

Evidence:

* The whole login phase is `ServerLoginPacketListenerImpl`. Grepping that file for `Neo:` /
  `neoforged` returns **no matches** — NeoForge does not patch it at all. The class implements only
  `ServerLoginPacketListener, TickablePacketListener` (`ServerLoginPacketListenerImpl.java:49`).
* NeoForge's own event list has nothing profile-related. The `PlayerEvent` subclasses documented at
  `_nfsrc_26.1.2\net\neoforged\neoforge\event\entity\player\PlayerEvent.java:35-50` are:
  `HarvestCheck, BreakSpeed, NameFormat, TabListNameFormat, Clone, StartTracking, StopTracking,
  LoadFromFile, SaveToFile, ItemCraftedEvent, ItemSmeltedEvent, PlayerLoggedInEvent,
  PlayerLoggedOutEvent, PlayerRespawnEvent, PlayerChangedDimensionEvent, PlayerChangeGameModeEvent`.
  A directory sweep for event classes matching `Login|Profile|Auth|User|Session|Connect` under
  `_nfsrc_26.1.2\net\neoforged\neoforge\event` returns only spawn-placement/respawn/spawn events —
  no `PlayerLoginEvent`, no `GameProfile` hook.
* The only two NeoForge hooks that fire during loading/saving expose the UUID **read-only**:

```java
// _nfsrc_26.1.2\net\eoforged\neoforge\event\EventHooks.java:502-508
public static void firePlayerLoadingEvent(Player player, PlayerList playerList, String uuidString) {
    NeoForge.EVENT_BUS.post(new PlayerEvent.LoadFromFile(player, playerList.getPlayerIo().getPlayerDir(), uuidString));
}

public static void firePlayerSavingEvent(Player player, File playerDirectory, String uuidString) {
    NeoForge.EVENT_BUS.post(new PlayerEvent.SaveToFile(player, playerDirectory, uuidString));
}
```

  `PlayerEvent.LoadFromFile` (`PlayerEvent.java:325-360`) stores `private final String playerUUID;` and
  only offers getters (`getPlayerUUID()`, `getPlayerDirectory()`, `getPlayerFile(String)`), with the
  comment *"The UUID is the standard for player related file storage."* It is fired **after**
  `player::load` (`PrepareSpawnTask.java:189-190`), i.e. after `Player.java:649` already reset the UUID —
  and it cannot change it.
* The cookie type is an immutable record (`CommonListenerCookie.java:6`) whose `gameProfile()` field is
  read at `ServerConfigurationPacketListenerImpl.java:58`, `PrepareSpawnTask.java:181` and
  `ServerConfigurationPacketListenerImpl.java:215`. `ServerConfigurationPacketListenerImpl#gameProfile`
  is `private final` (`:49`). The profile object itself is additionally immutable — authlib 7.0.63
  `com.mojang.authlib.GameProfile` is `public final class ... extends java.lang.Record` with fields
  `private final UUID id; private final String name;` and no setter (verified with `javap -p` on
  `authlib-7.0.63.jar` in the local Gradle cache). So neither the cookie nor the profile can be
  substituted through a supported mutation.
* The one extension point that *does* run between the cookie being built and the player spawning is the
  modded configuration-task queue:

```java
// ServerConfigurationPacketListenerImpl.java:140-141
// Neo: Gather modded configuration tasks and schedule them for execution
this.configurationTasks.addAll(net.neoforged.fml.ModLoader.postEventWithReturn(new net.neoforged.neoforge.network.event.RegisterConfigurationTasksEvent(this)).getConfigurationTasks());
```
  (`_nfsrc_26.1.2\net\eoforged\neoforge\network\event\RegisterConfigurationTasksEvent.java:21-27`,
  `ConfigurationTask` interface in `net.minecraft.server.network.ConfigurationTask`.)
  These tasks run *after* `PrepareSpawnTask` (added at `:116`) and `JoinWorldTask` (`:117`) in the same
  queue, so a task cannot observe or alter the spawn. It could technically disconnect/refuse a player,
  but not rewrite their UUID.
  Also available: `IServerConfigurationPacketListenerExtension#finishCurrentTask(ConfigurationTask.Type)`
  (`_nfsrc_26.1.2\net\eoforged\neoforge\common\extensions\IServerConfigurationPacketListenerExtension.java:15-22`)
  — same timing limitation.

**Conclusion:** no NeoForge injection point substitutes the UUID before playerdata load or before
`ServerPlayer` creation. The only ways are (a) a Mixin/coremod on `ServerLoginPacketListenerImpl`,
`CommonListenerCookie`, `ServerConfigurationPacketListenerImpl` or `PrepareSpawnTask`, or (b) calling
`Entity#setUUID` after the entity exists (see §4), or (c) wrapping/overriding `MinecraftSessionService`
(the `hasJoinedServer` return value) — the last is not an event, but it is the closest supported
substitution point since the profile originates there.

**Would whitelist/op/ban still work if the entity UUID differed from the Mojang profile UUID?**
Yes — all four checks are fed `NameAndId` derived from the **profile**, not from `Entity#uuid`:
`new NameAndId(this.gameProfile)` (`ServerConfigurationPacketListenerImpl.java:215`),
`new NameAndId(this.playerProfile())` (`ServerCommonPacketListenerImpl.java:223`),
`player.nameAndId()` → `new NameAndId(this.gameProfile)` (`Player.java:1338-1340`) used at
`PlayerList.java:351,359,370,485,598,602` and `MinecraftServer.java:1717`.
They would **not** work if the *profile* UUID were replaced (i.e. a forged session-service response or a
rewritten `usercache.json`), because the ops/whitelist/bans JSON is keyed by the old profile UUID string.
Note that `ServerLevel.addPlayer` warns on duplicate UUID using `player.getUUID()`
(`ServerLevel.java:1000-1004`), i.e. the entity UUID, so two players could still collide/not collide
independently of the list checks.

## 4. Changing the UUID of an already-created `ServerPlayer`

**Yes — `Entity#setUUID` is `public` and is inherited by `ServerPlayer`.** There is no player-specific
override and no `@Deprecated` on it.

```java
// Entity.java:280-281   (field)
protected UUID uuid = Mth.createInsecureUUID(this.random);
protected String stringUUID = this.uuid.toString();
```

```java
// Entity.java:3183-3195
public void setUUID(UUID uuid) {
    this.uuid = uuid;
    this.stringUUID = this.uuid.toString();
}

@Override
public UUID getUUID() {
    return this.uuid;
}

public String getStringUUID() {
    return this.stringUUID;
}
```

* Signature: `public void setUUID(UUID uuid)` — `public`, instance, `void`, no null-check, no side
  effects beyond the cached string. **No comment of any kind** at the declaration
  (`Entity.java:3183`); the only Forge/Neo annotation nearby is on an unrelated method
  (`Entity.java:3202`: `@Deprecated // Forge: Use FluidType sensitive version`).
* `server\level\ServerPlayer.java` contains **no** `setUUID` / `uuid` field of its own — grep over that
  file for `setUUID|uuid` returns only the vehicle attach UUIDs (`:463,477,481`). So `ServerPlayer`
  inherits the public setter unchanged.
* Callers of `setUUID` in the tree: `Entity.java:3796` and `LivingEntity.java:4036`
  (client-side `recreateFromPacket`), `TypedEntityData.java:135`,
  `server\commands\data\EntityDataAccessor.java:57` (which deliberately *preserves* the UUID around an
  NBT load, and refuses players: `if (this.entity instanceof Player) throw ERROR_NO_PLAYERS.create();`),
  and the two identity-resetting calls in `Player.java:182` / `:649`.
* The `uuid` field itself is `protected`, so a subclass/mod subclass can also assign it directly, but
  `stringUUID` (the cached string, used by `getStringUUID()` and therefore by
  `PlayerDataStorage.save`) is `private` — bypassing `setUUID` would desync the two.

**Consequences of calling `setUUID` on a live player (verified in code, not guessed):**

* Nothing re-indexes `playersByUUID` (`PlayerList.java:216`), so `PlayerList.getPlayer(uuid)` and
  duplicate-login checks go stale for the new UUID and still match the old one until the map is written
  again (only `placeNewPlayer`/`respawn` write it, `:216`, `:441`).
* `ServerLevel`'s `EntityLookup.byUuid` (`world\level\entity\EntityLookup.java:17`) is not re-keyed, so
  `level.getEntity(newUuid)` misses.
* Saving then uses the new UUID for the filename (`PlayerDataStorage.java:41-43`,
  `player.getStringUUID()`), while the old `<oldUuid>.dat` is left behind.
* `getScoreboardName()` (the UUID string) changes, and chat signature decoding was already bound to the
  old UUID at `ServerGamePacketListenerImpl.java:285/2190`.

I could **not** find any supported NeoForge API in the 26.1.2.114 API sources that changes a player's
UUID (grep for `setUUID` in `_nfsrc_26.1.2` returns nothing). Any such change is a direct call to
`Entity#setUUID` (or a Mixin), not an event-driven one.

## 5. What happens on the *next* login after a UUID change

The server **re-derives the original Mojang profile UUID** for the entity, so the player's data written
under the modified UUID is orphaned. Three independent mechanisms guarantee this:

1. **A fresh `ServerPlayer` is constructed from the login profile**, so `Player.java:182`
   (`this.setUUID(gameProfile.id())`) applies the profile UUID again before anything is loaded:

```java
// PrepareSpawnTask.java:181
ServerPlayer player = new ServerPlayer(PrepareSpawnTask.this.server, this.spawnLevel, cookie.gameProfile(), cookie.clientInformation());
```

2. **Even if the `UUID` tag in the saved NBT were the modified one, it is discarded.** `Entity.save`
   writes the current (possibly modified) entity UUID:

```java
// Entity.java:1985
output.store("UUID", UUIDUtil.CODEC, this.getUUID());
```
   and `Entity.load` reads it back:

```java
// Entity.java:2070-2073
input.read("UUID", UUIDUtil.CODEC).ifPresent(id -> {
    this.uuid = id;
    this.stringUUID = this.uuid.toString();
});
```
   but `readAdditionalSaveData` (called immediately afterwards at `Entity.java:2091`) unconditionally
   overwrites it from the profile:

```java
// Player.java:646-649
@Override
protected void readAdditionalSaveData(ValueInput input) {
    super.readAdditionalSaveData(input);
    this.setUUID(this.gameProfile.id());
```
   (`ServerPlayer.readAdditionalSaveData` calls `super` first — `ServerPlayer.java:414-416` — so the
   same reset happens for players.)

3. **Which file gets loaded is decided by the profile UUID, not the entity UUID**:
   `PrepareSpawnTask.java:187` passes `this.nameAndId` (built from the profile at `:115`) into
   `PlayerList.loadPlayerData` (`PlayerList.java:290-298`) → `PlayerDataStorage.load(NameAndId, ...)` →
   `new File(this.playerDir, nameAndId.id() + suffix)` (`PlayerDataStorage.java:65`).

Therefore, if a mod forced `Entity#setUUID(X)` during a session with profile UUID `P` (X ≠ P):

* This session saves to `players/data/X.dat`, `players/stats/X.json`, `players/advancements/X.json`
  (and stats/advancements maps were keyed by `P` during the *lookup* stage —
  `PlayerList.java:775` uses `gameProfile.id()`, `:805` uses `player.getUUID()` — so those two can even
  disagree with each other *within* one session if `setUUID` is called after login).
* On the next login the profile UUID is `P` again, so the server loads `players/data/P.dat`, builds
  `stats`/`advancements` under `P`, and registers `playersByUUID.put(P, player)`. The `X.*` files are
  never read again — effectively a silent data reset/duplication: the player appears with their
  pre-change data, and everything done under `X` is stranded on disk.
* `usercache.json` will also have been rewritten with whatever `player.nameAndId()` said at
  `placeNewPlayer` time (`PlayerList.java:145-149`), while `ops.json`/`whitelist.json`/
  `banned-players.json` keep the *profile* UUID string from when they were written.

**This is the mechanism a "new life / new identity" feature cannot rely on via `setUUID` alone:** the
canonical UUID is re-imposed from the session profile on every login, and the playerdata/stats/
advancements file names are computed from two different sources (profile UUID on load, entity UUID on
save).
