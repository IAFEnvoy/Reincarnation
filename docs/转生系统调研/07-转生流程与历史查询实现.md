# 转生流程与历史查询实现

> 更新于 2026-11-05；Minecraft 26.1.2、NeoForge 26.1.2.99、Java 25。
> 在 06 的基础桥接上补齐独立模组的转生、归档、恢复、处理器 API 和文字指令。本文描述当前代码；主设计的界面和具体修仙模组条目仍作为集成设计保留。

## 1. 入口与默认策略

`ReincarnationApi.reincarnate(ServerPlayer, ReincarnationRequest)` 在服务端主线程调用，返回替代玩家。账号 UUID、GameProfile 和连接保持稳定，后续逻辑必须使用返回值。

`ReincarnationRequest.atSpawn(player, reason)` 使用原版世界出生点；也可指定维度、位置、朝向、原因及 `ResetPolicy`。原因类型为 `Component`；指令入口要求文字非空且不超过 256 字符，Request 不再按服务端展开的文字校验原因。坐标/角度必须有限，维度须存在，世代不可溢出。

默认 `ResetPolicy(true, false, false, true)`：

| 项目 | 默认行为 |
|---|---|
| 背包/装备、末影箱、经验、玩家 Score | 清空，忽略 keepInventory 的普通死亡保留效果 |
| 食物、成长属性、药水、吸收、附魔种子 | 默认值 |
| 配方、统计、进度及缓存 | 清空并重新同步 |
| 肩上生物、旧重生点、珍珠、监守者计时、死亡坐标、定位条样式、计分板标签 | 重置 |
| 游戏模式 | 保留；可选择服务器默认模式 |
| 个人计分板分数 | 清除；可选择保留 |
| 队伍 | 保留；可选择清除 |
| 未知 NeoForgeData | 默认保留；可选择清除，再由处理器恢复明确保留项 |
| NeoForge 附件 | 默认清除；仅保留标签内且类型允许死亡复制、复制处理器未拒绝的可序列化附件 |
| OP、白名单、封禁、账号署名、Vault 领奖等裸 UUID 事实 | 保留 |

能力按所选游戏模式初始化，不继承前世飞行状态。属性使用新玩家构造时的 AttributeMap 与 supplier 默认值，不导入旧属性基值或修饰符；其他模组为新对象初始化的属性和处理器派生的跨世效果继续保留。

## 2. 事务与保存顺序

状态为 `PREPARED → COMMITTING → COMMITTED`；准备后未进入 COMMITTING 的记录在启动时转为 `ABORTED`。一个账号同时只允许一个事务；Pre 取消与重入在破坏性操作之前被拒绝。

当前进程只运行一个服务端，`ReincarnationService` 使用生命周期单例，无需按 `MinecraftServer` 建表。服务端启动前由 `start(server)` 创建实例并完成事务扫描；指令、事件、API 和 Mixin 统一使用无参 `get()`，尚未启动时拒绝访问；服务端完全停止后由 `stop()` 释放实例。恢复测试同样通过 stop/start 重建服务，重新读取磁盘状态。原来的 `get(server)`、`release(server)` 与公开的实例 `initialize()` 已删除。

1. 校验当前在线玩家和目标，触发 Pre。
2. 从当前内存归档完整玩家 NBT、鼠标携带物品、统计 JSON、进度 JSON、分数/队伍摘要、旧世 `SoulRecord` 和处理器快照。记录归档格式、MC 与模组版本，不依赖最近自动保存。
3. 使用 `FileAccess.NBT` 与 `CompoundTag.CODEC` 写入不可变 `archive.dat`，计算 SHA-256；使用 `LifeTransaction.CODEC` 保存 PREPARED 清单。
4. 保存 COMMITTING 意图，随后才关闭菜单、解除骑乘/乘客、移除飞行珍珠并幂等推进世代。
5. 停止旧进度监听器，仅驱逐该账号的 stats/advancements 缓存，写带 DataVersion 的空 JSON。UUID 文件存在后不触发按名字的旧统计回退。
6. 清旧重生点，调用 `PlayerList.respawn(old, false, CHANGED_DIMENSION)`。出生事件指定请求目的地、不复制旧重生点，避免消耗旧重生锚。新玩家构造完成后，跳过原版 `restoreFrom` 的批量继承，仅交接连接运行状态、补回策略允许的数据，再触发 Clone；跳过 NeoForge 默认附件复制和旧实体标签的继承，其余原版重生步骤与事件保留。
7. 更新 `connection.player`、位置跟踪和客户端加载计时。清理已加载旧关系，应用处理器和 Reset 事件；不再清除 Clone/Respawn 监听器为新玩家生成的数据。
8. 写 `PlayerPersisted["reincarnation:life"]`，包含 generation、transaction、started。普通死亡保留此标记。补发背包、选中槽、相机、属性、生命/食物、经验、统计、进度、配方及附件。
9. 依次通过 `FileAccess.JSON` 保存新统计与进度，再保存需要清理的计分板、新世摘要，最后由 `PlayerDataStorage.save()` 保存玩家。读取玩家存档检查新世标记，确认初始化结果已保存。
10. 发布旧世历史、当前摘要和 COMMITTED。最后触发 Post；通知异常只记录日志，不撤销已提交转生。

模组文件统一使用 Saturn 的 `FileAccess` 和 Codec 直接读写，已删除 `AtomicFiles`。归档使用 `CompoundTag.CODEC`，事务使用 `LifeTransaction.CODEC`，新世/当前世/历史摘要使用 `SoulRecord.CODEC`，世代索引使用自身 Codec；统计与进度使用 `ExtraCodecs.JSON`，保留原版 JSON 对象结构。目录由调用处创建；每次保存检查 boolean 结果，必要文件加载失败时抛错，不使用默认值掩盖损坏。

不再添加临时文件、force、原子替换或压缩层。NBT 为 `FileAccess.NBT` 的未压缩二进制格式，文件路径及业务版本号保持原样。此前用 `AtomicFiles` 保存的 GZIP 文件不能由新接口直接读取，本轮不提供旧文件自动转换，也不删除或覆盖无法解码的既有文件；旧索引读取失败仍会阻止启动。

原版玩家文件仍由 `PlayerDataStorage` 保存与加载；仅在新世初始化保存期间临时放行该玩家的保存守卫，其他待恢复玩家仍被阻止保存。读取校验使用底层 `PlayerDataStorage.load()`，避免再次进入 `PlayerList.loadPlayerData()` 的恢复钩子。原版方法可能吞掉 IO 异常，因此保存后仍检查新世标记。

MC 26 的计分板文件是 `data/minecraft/scoreboard.dat`。由 `storeToSaveDataIfDirty` 与 `SavedDataStorage.saveAndJoin()` 保存并等待后台任务结束。本模组不再自行重写玩家与计分板文件，也不改变它们的原版格式。

### 新对象与按策略继承

原版首次加入的入口是 `PrepareSpawnTask.Ready.spawn`：先 `new ServerPlayer(...)`，仅当玩家存档存在时才调用 `player.load(...)`。无存档时完全跳过 load；对旧对象加载空 NBT 并不能得到相同结果。

正常转生沿用原版 `PlayerList.respawn` 创建新玩家，在 `ServerPlayerLifecycleMixin` 中仅对当前转生调用替换 `restoreFrom`。`PlayerInheritance` 从归档补回游戏模式、策略允许的 NeoForgeData 和白名单附件，并交接有效聊天会话、区块跟踪视图、调试订阅和 Tab 页眉页脚。GameProfile、客户端设置、连接、实体 ID 和主手由原版创建及重生流程处理。背包、末影箱、食物、属性、配方、肩上生物、死亡位置等直接保留新对象初始值，不复制再清除。原来的 `PlayerReset`、重建 FoodData/末影箱的 Mixin 及无用访问器已移除。

`PlayerListLifecycleMixin` 同时让原版的旧实体标签循环在转生时读取空集合，新玩家在 Clone 中新增的标签不会被删除。普通死亡重生和末地返回不会进入上述专用继承作用域。

未知持久化 NBT 默认作为策略允许项合并到新玩家，`resetUnknownModData=true` 时不导入；不会替换或清空新对象已有的 PersistentData。正常转生在 Clone 前完成策略继承，随后监听器可初始化新世数据；完成阶段仅运行处理器、Reset 与保存。故障恢复仍通过空存档输入创建新玩家，在 LOWEST 登录恢复阶段补回允许项；也不再清除正常登录初始化的数据。已完成初始化的事务只补元数据的规则保持不变。

## 3. 故障恢复与保存保护

启动时在世界实体加载前扫描清单：

- PREPARED：标为 ABORTED，不改世代。只有归档而无清单的孤儿目录不重放。
- COMMITTING：校验归档哈希、格式、事务 ID 和必要处理器版本，补齐世代推进。
- 主玩家存档已有本事务的新世标记且进度文件可读：只补历史、摘要和 COMMITTED，保留已经产生的新世物品、经验和统计。
- 尚未初始化：准备空进度、驱逐旧缓存，在 `PlayerList.loadPlayerData` 返回空输入，阻止旧位置、RootVehicle 和珍珠数据进入新对象。真正登录时在该对象完成同一事务，不在 `placeNewPlayer` 内再次替换玩家。

运行失败也遵循同样规则。保存守卫阻止待恢复玩家、已移除对象及旧世对象覆盖存档，受影响连接断开。重新登录前再次检查初始化标记，不能看到 COMMITTING 就重复清空。提交意图已保存但索引尚未推进时，恢复会重试世代写入。

完成世代大于 0 时，加载结果必须有匹配的世代标记，缺失/旧世 `.dat` 或 `.dat_old` 不会被视为新世。损坏的全局世代索引仍须修复；扫描事务不等于能重建任意丢失的身份表。

处理器和 Reset 必须幂等，外部状态需按 txId 自行去重。这不是跨任意模组数据库的分布式事务，也未验收真实断电、磁盘控制器缓存或每阶段的进程强杀。

## 4. 通用引用与玩法关系

引用格式继续使用 06 的统一桥接，没有添加 Owner、Trusted 等字段专用格式适配。本轮修正两处共享边界：

- `TagValueOutput.buildResult()` 可能引用运行中 NBT 的分支，现在先复制完整输出再打包，避免元数据污染活实体的 PersistentData。
- 从归档抽取 NeoForgeData/附件前先调用 `ReferencePersistence.restore(NbtOps.INSTANCE, payload)` 并接收返回结果，再复制分支；不能把相对旧玩家根的路径表当作 PersistentData 搬入新玩家。旁表结构与联合编码现由 Codec 处理，通用路径导航使用 DynamicOps，不再手写 NBT 元数据。

`Relations` 只处理玩法结果：过期的宠物/马解除主人与驯服状态，NeutralMob 停止旧世持久愤怒，指向旧玩家对象的 Mob target 清除。转生处理已加载实体；之后的加载事件只排队，服务端 tick 再清理。不把“离线/暂未解析”当作过期，不强制加载所有区块。清理珍珠的区块票据前检查同区块仍存活的珍珠，保留其他玩家仍在使用的共享票据。

裸 UUID 不含世代，无法通用还原含义。村民声望、Warden 自定义记忆、数据库和领地等首版按账号事实保留；需要按世重置的玩法由所属系统接入。不会清空整个 Vault/试炼集合。

## 5. 存储布局

```text
<world>/
  data/reincarnation/generations.dat
  data/reincarnation/generations.dat.initialized
  reincarnation/
    transactions/<txId>/
      archive.dat       # 不可变旧世快照，清单中的 SHA-256 校验
      transaction.dat   # 状态、账号、from/to、请求、策略、归档哈希
      initialized.dat   # 初始化标记保存前生成的新世摘要
    history/<uuid>/<generation>.dat
    accounts/<uuid>.dat # 当前世最近摘要
  players/data/<uuid>.dat
  players/data/<uuid>.dat_old
  players/stats/<uuid>.json
  players/advancements/<uuid>.json
```

旧世历史按账号与世代追加，同事务重放幂等，不同事务不能覆盖已归档世代。当前摘要在登录、退出、原版保存和在线查询时刷新。索引和归档须随世界一起备份；首版不提供回滚、删除或自动裁剪历史指令。

## 6. 文字指令

| 命令 | 行为 |
|---|---|
| `/reincarnation`、`/reincarnation status` | 自己当前世详情 |
| `/reincarnation status <player>` | 指定玩家本世与待恢复状态 |
| `/reincarnation history` | 自己世代摘要 |
| `/reincarnation history <player> [page]` | 默认每页 8 条，可配置，最新世在前 |
| `/reincarnation info <player> <generation>` | 某一世详情，世数从 1 开始，1 查询第一世 |
| `/reincarnation rebirth [target] [reason]` | 管理员触发，目标须在线，支持单玩家选择器 |

player 支持在线名字、已记录离线名字和 UUID；名字歧义时要求 UUID。只查本地记录，不请求远程档案服务。普通玩家仅可查自己，查询他人和转生需要原版游戏管理员权限等级 2；控制台需指定目标。

信息包括姓名/账号、当前/结束状态、记录开始与结束时间、原因、位置、模式、经验、背包数、进度数、死亡、游戏时间、事务号。第 1 世从首次记录开始，安装前生涯不可推算；离线当前世是最近摘要。背包计数不包括末影箱和第三方额外容器，完整原始玩家 NBT 另存归档。

所有玩家可见的世数为内部世代 ID 加 1，统一通过 `LifeNumbers` 转换；存档、引用、历史文件名、事务与 API 上下文仍使用从 0 开始的内部 ID。查询参数反向转换后读取原有记录，不改写旧数据。转换支持整个非负 long 范围，内部 `Long.MAX_VALUE` 显示并可查询为 `9223372036854775808`，避免加 1 溢出；参数 0、负数、非整数和超范围数字返回可翻译错误。

## 7. 扩展契约

```java
modBus.addListener((RegisterReincarnationHandlersEvent event) -> event.register(new MyLifeHandler()));

// 服务端主线程；后续改用 fresh。
ServerPlayer fresh = ReincarnationApi.reincarnate(player,
        ReincarnationRequest.atSpawn(player, Component.literal("寿元耗尽")));
```

`ReincarnationHandler` 用唯一 Identifier、版本、优先级登记，按 priority 再按 ID 排序，重复 ID 拒绝，注册后冻结。

- `archive(player)` 返回可复制的 CompoundTag 快照，不能先清空再归档。
- `reset(fresh, context, snapshot)` 按快照幂等设置状态；`recover` 默认调用 reset，可覆盖以适配外部系统。
- context 包含 txId、账号、from/to、请求和 recovering。
- 事务保存参与处理器的 ID/版本。恢复缺少参与者或版本不匹配时拒绝；之后新增的处理器不参与旧事务重放。
- Pre 可取消，Reset 可能重放；跨世保留要在处理器/Reset 中完成。Post 只是通知，不能承载必要恢复动作。

当前工程已引入 Jupiter 与 Saturn，未引入 MortalCultivation、MXT、Curios 依赖。灵根、功法、资源加成账本和额外装备规则由所属模组接入；附件标签只定义整个类型是否允许复制，不定义类型内部的玩法重置语义。非序列化附件、序列化器自行跳过的内容及外部文件不在默认归档承诺内。

## 9. 翻译与原因数据

## 10. Jupiter 配置与 Saturn 依赖

构建通过 CurseMaven 引入与 MiXianTu 相同的 Jupiter `8569832`（2.4.2）和 Saturn `9393421`（1.1），元数据将二者声明为双端必需依赖，加载顺序在它们之后。

`ReincarnationServerConfig` 使用 `AutoInitConfigContainer`，注册到 Jupiter 的服务端配置管理器，远程读取与修改使用 `PermissionChecker.IS_OPERATOR`。客户端独立注册 `IConfigScreenFactory`，通过模组列表打开配置选择界面。配置文件为 `config/reincarnation/reincarnation-server.json`，可由 Jupiter 界面保存，也可手动修改后 `/reload`。

| 配置 | 默认值 | 作用 |
|---|---|---|
| `lifecycle.auto_reincarnate_on_death` | `false` | 玩家死亡后重生时自动开启新世 |
| `lifecycle.filter_death_damage_types` | `false` | 自动死亡转生仅接受 `reincarnation:reincarnate_on_death` 内的最终致死伤害类型 |
| `reset.scores` | `true` | 重置个人计分板分数 |
| `reset.team` | `false` | 将玩家移出计分板队伍 |
| `reset.unknown_mod_data` | `false` | 清未知模组持久化 NBT，并禁止附件标签自动保留；处理器仍可恢复自身数据 |
| `reset.keep_game_mode` | `true` | 沿用前世游戏模式，否则使用服务器默认模式 |
| `query.history_page_size` | `8` | 历史每页条数，范围 1–50，由 Jupiter Codec 校验 |

`atSpawn` 工厂读取当前配置并生成不可变 `ResetPolicy`。请求进入事务后，其重置策略随原有事务格式保存；改配置或重载配置不会改变待恢复事务。显式构造请求的调用者仍指定自己的策略，`ResetPolicy.DEFAULT` 保持固定的基准默认值。

## 11. 死亡后自动转生

`lifecycle.auto_reincarnate_on_death` 默认 `false`。开启后在 `PlayerList.respawn` 入口检查玩家死亡状态和 `keepAllPlayerData`，死亡重生进入现有事务协调器。原因优先使用死亡事件保存的 `reincarnation:death_reason` 组件，寿元伤害记录为 `reason.reincarnation.lifespan`，普通死亡回退 `reason.reincarnation.death`；该附件使用 Component Codec 持久化，不随重生复制，死亡界面停留过久也不会遗失原因。保留原版死亡界面和死亡处理；末地返回与存活玩家的重建不触发。归档包含本次死亡的统计；原版死亡时已经产生的掉落保持原版语义。极限模式的观战规则仍由原版重生请求处理。

可选 `lifecycle.filter_death_damage_types` 默认 `false`。同时开启时，自动入口在新建事务前检查最终致死伤害是否属于 `DamageTypeTags.REINCARNATE_ON_DEATH`（`reincarnation:reincarnate_on_death`）。数据文件为 `data/reincarnation/tags/damage_type/reincarnate_on_death.json`，默认只含 `reincarnation:lifespan`，允许数据包追加或覆盖，支持 `/reload`。死亡事件使用最低优先级记录最终 `DamageSource` 的 damage type 注册表键，保存到 `reincarnation:death_damage_type` 附件；该键通过 Codec 随玩家持久化，不复制给新玩家。先前非致死攻击不参与，原版最近伤害来源过期不影响判定。重生时按当前 tag 判断，未命中、空 tag 或无记录时直接普通重生，不归档、不推进世代。手动/API 和寿尽直接转世不受影响。

`death_damage_filter`、`death_damage_saved` 覆盖最终一击、两个配置开关、空 tag、tag 更新、无记录、普通重生与直接转世、附件不继承、玩家 NBT 持久化，以及死亡界面等待 65 tick 后的判定。`build runGameTestServer` 全部 40 项必需测试通过，见 `build/death-damage-tag-validation.log`。

协调器内部重建玩家时通过 `busy` 状态跳过自动入口，因此同一死亡只提交一个新世。转生按当前配置创建重置策略快照，`keepInventory` 不阻止新世重置。提交前取消或出错返回普通重生并给出可翻译提示；提交意图持久化后出错则沿用原事务断线恢复，阻止继续普通重生和半成品保存。关闭开关或修改 tag 不影响已提交事务的恢复。

`lifecycle_death` 使用真实 `hurtServer` 致死以及 `PERFORM_RESPAWN` 请求，验证关闭时保留原世、开启后连续推进、旧世引用失效、死亡统计归档、背包/末影箱/经验清空、重复重生请求、末地返回、Pre 取消和处理器失败；重新构建协调器并登录后完成同一事务，世代不再次推进。

原版 `LivingEntity.tickDeath` 会在死亡 20 tick 后将尸体以 `KILLED` 移出世界，此时玩家仍在 `PlayerList` 中、连接仍然有效。转生入口允许当前在线会话的这种死亡尸体继续归档与重建；同时验证账号对应的玩家对象、连接绑定对象、断线标记和连接状态，其他移除原因仍然拒绝。

`lifecycle_delayed_death` 用真实 `/kill` 指令致死，推进 25 次连接 tick，在第 35 tick 发出重生请求。EmbeddedChannel 不在服务器网络监听器中，必须显式推进连接 tick 才会执行原版尸体移除。测试先在旧校验下复现 `error.reincarnation.offline`，修复后确认新世完整重置、一次归档、旧对象不能再次转生、非死亡移除和已关闭连接被拒绝。复现日志：`logs/delayed-death-reproduction.log`；修复后全量验证：`logs/delayed-death-verification.log`。

## 12. 附件保留标签与事件顺序

`ReincarnationTags.KEEP_ON_REBIRTH` 为附件注册表上的 `reincarnation:keep_on_rebirth`。NeoForge 26.1.2.99 的 `ATTACHMENT_TYPES` 使用普通 `MappedRegistry`，参与服务端静态注册表 tag 加载和重载；资源路径为 `data/reincarnation/tags/neoforge/attachment_types/keep_on_rebirth.json`。默认文件 `values: []`，全部附件默认清除。数据包或其他模组可用同名资源追加附件 ID；可选模组条目使用 `{"id":"othermod:player_data","required":false}`。

自动保留必须同时满足：事务开始时已存在该附件、类型在 tag 内、类型声明 `copyOnDeath()`、归档包含其序列化数据、复制处理器返回非 null。`AttachmentTypeAccess` 只读取 NeoForge 的 `copyOnDeath` 与 `copyHandler` 字段，不修改附件声明。从原始归档先筛选再解码，仅对保留项调用类型自己的复制处理器写入新玩家，不遍历移除目标玩家的附件。自定义处理器返回 null 时不写入旧值。正常转生在 Clone 前完成该步骤，`AttachmentInternalsMixin` 仅跳过当前转生中 NeoForge 默认 `onPlayerClone` 的自动复制，避免排除项的处理器产生副作用及保留项重复复制。其他模组显式编写的 Clone 逻辑、直接复制调用与新世初始化仍执行；处理器和 Reset 事件仍可显式恢复数据。普通重生不使用此筛选。

不可变 `archive.dat` 增加 `kept_attachments` 字符串列表，随原始数据一起受 SHA-256 校验。恢复使用归档名单，从相同原始值重放复制，不依赖后续 tag 重载结果、不把失败后的半成品再当作复制源。旧归档没有该字段时按空名单处理；已完成的新世只补齐事务元数据时仍不重置。`reset.unknown_mod_data=true` 可禁止所有标签自动保留。

`PlayerRespawnPositionEvent`、`PlayerLoggedInEvent`、`PlayerLoggedOutEvent` 的本模组监听均为 `EventPriority.LOWEST`。正常转生的策略允许项在 Clone 前补入，调用 `PlayerList.respawn` 返回后才执行处理器、Reset 和新世保存，因此落盘时所有同步 Clone/Respawn 监听器已经结束，也不会再全量清除其初始化结果。旧世快照仍在破坏性操作前保存，不能推迟到 Clone 后，否则无法可靠恢复旧世。登录恢复在 LOWEST 执行；同为 LOWEST 的监听器相对顺序仍取决于总线注册顺序，异步任务不属于此顺序保证。

新增 `AttachmentTests` 位于 main source set 的 gametest 子包，沿用主模组条件注册。完整验证通过 20 项必需测试；检查空 tag 的真实资源加载、tag 与类型自身规则的交集、自定义复制处理器、失败后重建协调器和登录恢复、tag 改变后保留名单稳定，以及事件顺序进入实际 `.dat` 的结果。
