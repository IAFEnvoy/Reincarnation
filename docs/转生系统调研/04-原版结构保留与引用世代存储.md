# 原版结构保留与引用世代存储：二次调研

> 基线：Minecraft 26.1.2、NeoForge 26.1.2.99、Java 25；2026-11-01。
> 本报告区分源码确认、独立原型验证与尚待游戏验证的设计。源码位于旧工程的 `.gradle/reincarnation-source-review/`，结论及后续工作以 Reincarnation 工程为准。
> 后续决策：用户要求避免逐关系适配，最新主线改为 [05-通用EntityReference持久化桥接.md](05-通用EntityReference持久化桥接.md)。本报告的附件布局与槽位适配保留为候选研究，不再作为默认实施路线。

## 1. 当时结论（候选，当前主线见 05）

**可以保留所有原版关系字段、`EntityReference.codec()` 和 `streamCodec()` 的原有格式。本轮候选曾建议把引用世代持久化到持有者的 NeoForge 数据附件，运行时再恢复到 `EntityReference` 的扩展字段。** 不必给每个 `Owner` 旁边增加一套自定义根键，也不必改变 UUID 的表示；其槽位适配成本促成了后续 05 的通用方案。

例如狼引用玩家：存档的持有者是狼，`Owner` 仍然是原版玩家 UUID；世代附件也放在狼上，不能只放在玩家上。否则没有记录“这条关系建立于第几世”，依然无法区分前世宠物与今世宠物。

如果“不改变原版结构”的要求更严格，连标准 NeoForge 扩展数据也不允许增加，则可以用独立 SavedData/文件记录 `(持有者身份, 关系槽位, 目标 UUID) → 世代`。但这只对身份可持续追踪的对象可靠：蜂巢、物品收纳及复制等身份丢失边界需要另外适配，不能承诺无附加身份信息也能普遍处理任意搬运。

## 2. 方案比较

| 方案 | 原版字段/叶子 Codec | 世代放在哪里 | 适用性 |
|---|---|---|---|
| NeoForge 持有者附件（本轮候选） | 全部保留 | 标准 `neoforge:attachments` 内注册本模组附件 | 元数据随持有者 NBT 保存，适合实体与方块实体；当前不作为主线 |
| `NeoForgeData` 内命名空间数据 | 全部保留 | 已有 `NeoForgeData` 扩展区 | 可行；类型、复制和迁移需自行管理 |
| 独立 SavedData/文件 | 实体/方块 NBT 不增加模组键 | 世界级旁库 | 适合有稳定身份的持有者，需处理事务与身份变化 |
| 父级新增 `reincarnation:Owner` 等键 | 保留 | 每个引用字段的父对象 | 上一轮方案 A，仍可作为无附件载体的备用适配 |
| `Owner` 改为 `{uuid,generation}` | 改变 UUID 输入类型 | 叶子对象 | 原版 UUID Codec 不接受，不作为兼容默认方案 |
| UUID 数组追加世代 | 改变数组长度 | 原字段 | 原版严格要求四个 int，不可行 |

附件方案保留的是原版字段结构，不是整份实体 NBT 逐字节不变；它会使用 NeoForge 已提供的扩展区。要求整份实体 NBT 不添加任何数据时，应选择外部旁库并接受其覆盖边界。

## 3. 为什么无法只靠叶子 Codec 无损塞进世代

`UUIDUtil.java:23-24` 使用 `Codec.INT_STREAM` 并调用 `Util.fixedSize(list,4)`。四个 int 已完整表示目标 UUID，没有额外的 generation 位置。把数组变长、换成对象、把世代写入 UUID 比特，都会改变原版输入或目标身份。

`TagValueInput.java:47-63` 先取 `input.get(name)`，然后将**这个字段值**传给 `codec.parse`。叶子 Codec 看不到包含它的整个父对象。`TagValueOutput.java:36-49` 也只把编码结果放在指定字段下。

所以，只替换 `EntityReference.codec()`，同时要求其输出仍是完全相同的 UUID 四整数值，不可能再从该值独立读回一个额外的任意世代。Codec 的解码余项、忽略未知键或 `MapCodec` 不会凭空增加信息；必须提供一个真实的外部存储位置。

`RegistryOps` 可以携带注册表上下文，但并没有自动提供“当前持有者、字段名和列表索引”。自定义 DynamicOps/作用域上下文可以传递这些信息，仍需持久化到附件或旁库，而且会增加存储封装、嵌套读取和静态 Codec 兼容成本。当时据此选择槽位适配；后续 05 改为标记叶子并遍历完整 NBT 自动取得路径，避免逐关系适配。

## 4. 候选附件布局与数据职责

```snbt
{
    UUID: [I; 1, 2, 3, 4],             // 狼自身 UUID，仍为原版格式
    Owner: [I; 123, 456, 789, 1011],  // 玩家 UUID，仍为原版格式
    "neoforge:attachments": {
        "reincarnation:reference_stamps": {
            version: 1,
            slots: {
                owner: {
                    target: [I; 123, 456, 789, 1011],
                    generation: 3L
                }
            }
        }
    }
}
```

NeoForge 已有此存储结构：`AttachmentHolder.java:27,120-137` 定义扩展键并按已注册附件类型分别保存。`.99` 的 Codec 附件 API 接收的是 **MapCodec**（`AttachmentType.java:196-228`），无需修改原版 `EntityReference.CODEC`。

数据职责：

- 世界级世代索引：记录玩家当前世代，转生事务的权威来源。
- 持有者附件：记录此持有者的每条关系绑定于哪一世，作为关系戳的持久化来源。
- `EntityReference` 扩展字段：运行时缓存已经绑定/恢复的世代，集中执行 `getEntity` / `matches` 检查。
- 原版 UUID 字段：继续承担身份查找、原版兼容和原有网络同步。

槽位采用稳定的语义标识，如 `owner`、`anger`、`last_hurt_by_player`；狐狸使用 `trusted/0`、`trusted/1` 并校验目标 UUID。多个槽位可以指向同一玩家但绑定不同世代，因此附件不能简单做成 `Map<玩家 UUID,世代>`。槽位重排或变更时，由适配器一起更新戳。

本模组内可使用下列附件序列化载体（这里只定义格式，不是完整运行时服务）：

```java
public record BoundReference(UUID target, long generation) {
    public static final Codec<BoundReference> CODEC = RecordCodecBuilder.create(i -> i.group(
        UUIDUtil.CODEC.fieldOf("target").forGetter(BoundReference::target),
        Codec.LONG.validate(g -> g >= 0L
            ? DataResult.success(g)
            : DataResult.error(() -> "Negative player generation"))
            .fieldOf("generation").forGetter(BoundReference::generation)
    ).apply(i, BoundReference::new));
}

public record ReferenceLedger(int version, Map<String, BoundReference> slots) {
    public static final MapCodec<ReferenceLedger> MAP_CODEC = RecordCodecBuilder.mapCodec(i -> i.group(
        Codec.INT.fieldOf("version").forGetter(ReferenceLedger::version),
        Codec.unboundedMap(Codec.STRING, BoundReference.CODEC)
            .fieldOf("slots").forGetter(ReferenceLedger::slots)
    ).apply(i, ReferenceLedger::new));
}
```

版本号、槽位与目标校验由装载服务执行；未知格式版本进入迁移/隔离分支，不能当成当前世代。正式附件默认值为空账本，空账本可以不保存。需要实体转换继承时配置 `copyOnDeath()`，但复制时仍需校验目标实体实际保留了哪些关系。

## 5. 接入顺序：不能只挂保存/加载末尾

已确认的 `.99` 顺序：

1. `Entity.saveWithoutId` 在 `Entity.java:2020-2023` 保存附件和 NeoForgeData，随后 `:2025` 调用子类 `addAdditionalSaveData`。
2. `Entity.load` 在 `:2087-2088` 读取 NeoForgeData 和附件，随后 `:2091` 调用子类 `readAdditionalSaveData`。

因此，**保存时附件早于多数关系字段编码**。不能等自定义叶子 Codec 被调用时才往附件账本补戳，否则当前保存已经写完附件。新绑定时就要更新账本，保存前可再做一致性核对；不能在保存时把缺失戳直接补为当前世代。

加载时附件先到，这对恢复很有利，但要在引用第一次被使用前恢复运行时戳。`NeutralMob.java:53-54` 在读入愤怒引用后立即调用 `getLivingEntity`；仅在 `Entity.load` TAIL 统一恢复会太晚。应在对应关系赋值/读取返回处，从已加载附件查出槽位和目标，恢复戳后才允许解析。

建议首版接入：

- `TamableAnimal`、`AbstractHorse`：主人新绑定时记账；主人读取时还原，不改变 Owner 序列化。
- `LivingEntity`、`NeutralMob`、`Animal`：伤害/愤怒/繁殖关系赋值和读入时同步戳。
- `Projectile`、TNT、区域效果：发射者/所有者绑定和读取时同步戳；保留珍珠等特有的注销与票据逻辑。
- `Fox`：直接使用 `TRUSTED_LIST_CODEC`（`Fox.java:132,429-442`），按实际信任槽位恢复账本，不依赖重写列表 Codec。

`EntityReference` 只保留运行时绑定、缓存命中校验、两个 getEntity 重载和 matches 的集中逻辑。不要仅为了持久化修改 UUID Codec、StreamCodec 或 equals/hashCode。原版 setter、直接字段赋值和第三方绕过入口仍需审计；不存在“注册一个附件就覆盖所有关系”的自动机制。

## 6. 搬运、转换与卸载

### 蜂巢：附件比外部 UUID 索引更适合

`BeehiveBlockEntity.java:55-82` 的剥离名单包括 `UUID`，但不包括 `neoforge:attachments` 或 NeoForgeData。`Occupant.of` 在 `:394-402` 保存完整蜜蜂后只删除名单中的字段；释放时 `:412-416` 再次按相同名单剥离。

由此可从源码判断：**附件戳有路径随蜜蜂的嵌套 NBT 进入蜂巢并在释放时保留，原蜜蜂 UUID 则会丢失**。`TypedEntityData.codec()` 对其余 CompoundTag 内容整体保留（`TypedEntityData.java:39-62`），也支持这一保存路径。此处是源码结论，尚未实际进游戏验证蜂巢物品搬运。

### 转换与方块实体

`AttachmentInternals.java:53-63` 的 living conversion 按死亡复制策略处理，需 `copyOnDeath` 或专用复制器。它只复制附件，不保证所有子类原版关系都被转换逻辑保留；复制后仍要按实际关系清理多余槽位。

方块实体也有标准附件读写（`BlockEntity.java:101-120`）。但方块实体变成物品时，不保证其附件自动成为物品组件；应核对具体方块的搬运路径。独立物品数据如确需扩展，应优先使用已有 `minecraft:custom_data` 命名空间内容并保留原组件值，而不是假设实体附件能够自动覆盖任意 ItemStack。

### 卸载兼容的准确表述

原版 Owner/Trusted 等值仍可读取。纯原版通常忽略 NeoForge 扩展区；仍使用 NeoForge 但卸载本模组时，`AttachmentHolder.java:154-157` 会记录未知附件并跳过它，不会因该附件类型缺失就必然拒绝整只实体。

这不保证世代数据能跨卸载重保存而保留。未知附件可能被丢弃；没有本模组时也不会执行前世隔离。若需要导出成纯原版语义，应在卸载前物理断开已过期关系，而不是保留旧 Owner 再期待原版知道其世代。

## 7. 严格不增加原版 NBT 键：外部旁库的边界

可选键为 `(world, holderKind, holderId, slot, targetUuid)`；实体持有者以自身 UUID 标识，方块实体以维度＋坐标标识。普通实体卸载、重新加载和跨维度移动可追踪；新绑定、解绑、实体转换及克隆必须同步旁库。旁库与玩家世代日志还需处理崩溃时的一致性，不能只依靠存档 mtime。

这种方案不能仅凭目标玩家 UUID 或当前世代推断关系。反例：一只前世狼和一只今世狼 Owner 相同；必须有持有者键区分两条关系。进一步，若搬运后持有者身份被原版剥离，且两个序列化载荷完全相同，外部系统无法仅从这些相同数据恢复它们不同的历史世代。

所以“不给载荷增加任何身份标记 + 任意复制搬运后仍精确区分历史关系”不能作为一般保证。可通过限制覆盖对象、拦截每个已知搬运边界转移旁库记录，或允许附件/扩展元数据解决。首版推荐附件账本，外部索引用于需要查询或无法使用附件的已知持有者。
